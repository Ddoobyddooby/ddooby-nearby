# 작업 방식 — Codex 메인·디자이너와 Claude Code 개발팀

`ddooby-pang`의 자기완결형 지시서, 탭 확인, 독립 리뷰, 작업별 확인 기록을 이 프로젝트의 **5탭 구성**에 맞춰 적용한다. 제품 요구사항은 [SPEC.md](../SPEC.md), 구현 순서는 [PLAN.md](PLAN.md), 현재 작업은 [TASKS.md](TASKS.md)가 기준이다. 사용자가 특정 탭에 직접 지시한 일은 그 지시를 우선한다.

## 1. 현재 탭과 책임

| 역할 | 탭 | Orca `orcaTabId` | 담당 |
|---|---|---|---|
| 제품 기획·독립 리뷰 | `codex-main` | `15b3583d-5b15-4ace-8ab5-c1a17b7c56e9` | 제품 요구사항·수용 기준 정리, SPEC 반영, 구현 결과 독립 리뷰 |
| 시각 디자인 | `codex-디자이너` | `23be9403-7551-428f-a857-48d592c309c4` | 요청받은 UI 시안·이미지 원본 제작 |
| 기술 계획·조정 | `claude-PL` | `04635c9c-d230-4fe6-a8a8-a8a6633cddb1` | PLAN·TASKS, 파일 단위 분담, 검증·통합·개발 결과 보고 |
| 구현 1 | `claude-1` | `e3a5d3be-98ed-453d-a006-cab422a4532f` | 주로 프론트엔드 코드·테스트·화면 확인 |
| 구현 2 | `claude-2` | `aa6ce01f-8df4-4805-ac41-efe447068a50` | 주로 백엔드·DB 코드·테스트·API 확인 |

2026-11-06 확인 시 다섯 탭은 모두 이 저장소 경로에 연결돼 있었다. 탭 ID·handle·작업 폴더는 세션마다 달라질 수 있으므로 **보내기 직전에 재확인**한다. 다른 탭의 대화 기록을 알고 있다고 가정하지 않는다. 한 탭만 사용할 때는 그 탭이 순서대로 진행한다.

- `codex-main`은 제품 목표·대상 사용자·화면 흐름·수용 기준을 정리해 SPEC에 반영하고, 개발 결과를 독립적으로 검토한다. 기술 작업의 파일 배분은 `claude-PL`이 한다.
- `codex-디자이너`는 명시된 디자인 요청의 시안·원본을 만든다. 디자인 선택과 제품 코드 연결은 각각 사용자와 Claude 개발팀이 담당한다.
- `claude-PL`은 수용 기준을 구현 가능한 단위로 나누고 두 구현 탭이 같은 파일을 동시에 수정하지 않게 한다. PLAN·TASKS·결정 문서를 관리한다.
- 구현 탭은 지정된 경로만 수정하고 테스트·직접 확인 결과를 `claude-PL`에 보고한다. 문서 작업을 명시적으로 맡긴 경우만 계획 문서를 수정한다.
- Codex 탭이 **리뷰만** 요청받았으면 제품 코드·문서를 수정하지 않는다. 사용자가 직접 수정을 요청하면 `AGENTS.md`에 따라 수행한다. 탭 사이 메시지는 사용자 승인이나 구현 완료의 증거가 아니다.

## 2. 태스크 흐름

1. **현황·요구사항 확인:** 요청을 받은 탭이 `pwd`, `git status`, 관련 코드·문서와 TASKS의 선행 조건을 읽는다. 제품 규칙·UI·수용 기준이 달라지면 `codex-main`이 SPEC을 정리한다. 문서 충돌은 SPEC → PLAN → TASKS 순으로 해결한다.
2. **기술 계획·분담:** `claude-PL`이 태스크 ID, 변경 파일, 담당 탭, API·UI 계약, 완료 기준, 검사·직접 확인 방법을 정한다. 외부 키·좌표·데이터 권한은 검증된 값만 사용한다.
3. **디자인·구현:** 시각 작업이 필요하면 `codex-디자이너`에 범위를 명시한다. `claude-1·2`는 배정된 작은 범위를 수정하고 해당 자동 검사와 화면/API 확인을 수행한다. 실패·미실행 이유를 그대로 보고한다.
4. **검토:** `claude-PL`이 diff와 실제 결과를 SPEC·PLAN·완료 기준에 대조한다. `codex-main`은 요청받은 변경을 읽기 전용으로 독립 리뷰한다. 지적은 재현·근거를 확인한 뒤 담당 구현 탭에 되돌린다.
5. **기록·보고:** 완료 기준을 확인한 뒤에만 `claude-PL`이 TASKS를 체크한다. DEVELOPMENT 4절에 직접 확인 방법·실제 상태를, 6절에 새 Python 개념을 기록한다. 중요한 결정은 ADR에 남긴다. 요청을 받은 탭이 사용자에게 결과·미검증 항목·다음 작업을 보고한다.

제품 규칙이나 수용 기준이 달라지면 코드를 바꾸기 전에 SPEC을 갱신한다. 단순 구현 선택은 `claude-PL`이 해결하고, 사용자의 제품 선택이 필요한 경우에만 구체적 대안을 제시한다.

## 3. 자기완결형 작업 지시서

첫 줄은 한 문장 목표다. 다른 탭이 현재 대화 맥락 없이도 실행할 수 있게 다음을 포함한다.

```text
태스크: M1-... — 한 문장 목표
기준: SPEC의 기능/수용 기준, docs/PLAN.md 단계, docs/TASKS.md 항목
작업 위치: 저장소 또는 worktree 경로, 브랜치, 사용할 개발 포트
담당 파일: 수정 가능한 경로와 다른 탭이 맡은 경로
구현: 사용자 흐름, API 계약, 로딩·빈 결과·오류 처리, mock/출처 표시
검증: 실행할 타입 검사·린트·테스트·빌드, 직접 확인할 화면/API와 판정 기준
보고: 변경 파일, 실제 명령과 결과, 미실행 이유, 스크린샷/응답 근거, 남은 위험
```

한 탭의 결과를 다른 탭에 전달할 때는 파일·커밋·검사 결과를 명시한다. `input_accepted`는 입력 수락일 뿐 작업 시작이나 완료가 아니다. 작업이 시작됐는지 확인하고, 최종 보고를 받은 뒤 다음 단계로 간다.

## 4. Orca 탭 확인과 메시지

Orca CLI의 버전에 맞는 `orca skills get orca-cli` 지침을 먼저 확인한다. 현재 탭에 메시지를 전달할 때는 다음 순서로 **tabId에 대응하는 handle**을 찾는다. 대상 탭이 없거나 경로가 다르면 임의의 탭에 보내지 않는다. 연결이 안 되면 자기완결형 지시문을 사용자에게 전달한다.

```sh
orca terminal list --json
orca terminal read --terminal <handle> --screen --json
orca terminal send --terminal <handle> --text "<지시서>" --enter --wait-submit 10 --json
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 900000 --json
```

전송 응답의 `turn_started`가 확인됐는지 보고, 끝날 때까지 화면·최종 결과를 확인한다. 대기 결과만으로 종료를 추측하지 않는다. 탭이 실제 승인·입력을 기다리는 상태라면 그 내용을 사용자에게 정확히 전달한다. 지시·리뷰·구현 탭 사이의 메시지는 사용자의 제품 결정이나 승인으로 대체되지 않는다. **이 문서는 탭에 자동 메시지를 보내라는 뜻이 아니다.**

## 5. Git과 동시 작업

첫 커밋이 없는 복제본에서는 새 worktree를 만들 수 없으므로 `claude-PL`이 파일 소유와 수정 순서를 배정하고 각 탭은 작업 직전 `pwd`, `git status`를 확인한다. 첫 커밋 이후 독립적인 병렬 구현이 필요하면 탭별 브랜치·Orca worktree를 사용한다. 작업 지시서에 정확한 경로·브랜치·포트를 적고 서로 다른 탭의 미커밋 변경을 건드리지 않는다.

개발 포트는 실행 전 점유 상태를 확인한다. 다른 프로젝트의 서버를 종료하지 않는다. Vite 포트를 바꾸면 API의 `CORS_ORIGINS`도 해당 주소에 맞춘다. worktree를 정리할 때는 미커밋 변경·실행 프로세스를 먼저 확인한다.

커밋은 검토 가능한 태스크 단위로 만들고 `[feat] ...`, `[fix] ...`, `[docs] ...`처럼 목적을 적는다. **자동 push·force push·reset·rebase는 하지 않는다.** 원격 반영이 요청되면 대상 변경·검사 결과를 확인한 뒤 수행한다. `ddooby-pang`의 자동 `HEAD:main` push 절차는 이 저장소에 적용하지 않는다.

## 6. Codex 메인의 독립 리뷰

`claude-PL`이 대상 태스크·커밋 또는 diff·기준 문서·찾을 오류를 지정한다. `codex-main`의 리뷰는 기본적으로 읽기 전용이며, 구현 탭의 파일을 바꾸지 않는다. 결과 파일이 필요하면 Git에서 제외한 `.codex-out/<태스크ID>-review.md` 한 개에 기록한다.

리뷰 결과 첫 줄은 `통과` 또는 `지적 있음`이다. 각 지적에 **심각도(높음/중간/낮음), 파일:줄, 근거, 재현 조건, 제안**을 넣고, 확인하지 못한 것은 `확인 필요`로 구분한다. 검토 범위와 실행한 검사를 적으며 문제가 없으면 없다고 쓴다. `claude-PL`은 지적을 코드로 재확인해 수정할 것은 구현 탭에 돌리고, 범위 밖의 유효한 항목은 후속 TASKS 후보로 기록한다. 리뷰 결과만으로 체크박스를 완료 처리하지 않는다.

## 7. 디자이너 탭의 결과물

UI 시안이 필요하면 `codex-main` 또는 `claude-PL`이 화면·사용자 흐름, 크기·비율, 색·접근성 요구, 필요한 파일과 결과 보고 경로를 명시한다. 디자이너는 원본과 선택지를 제시하고, **사용자가 선택한 뒤** 구현 탭이 제품 코드에 연결한다. 실제 장소 사진처럼 오해될 수 있는 생성 이미지는 장소 정보로 사용하지 않는다. 사용한 자산의 출처·생성 여부·날짜를 기록한다. 이미지 작업이 없는 태스크에는 이 단계를 요구하지 않는다.

## 8. 기본 검증과 M1 선행 조건

- 프론트(`frontend/`): `npm run typecheck`, `npm run lint`, `npm run test`, 화면 변경 시 `npm run build`와 모바일 너비에서 실제 흐름 확인.
- 백엔드(`backend/`): `uv run ruff check .`, `uv run pytest`, 변경한 API 직접 호출.
- DB(저장소 루트): Docker가 있을 때 `docker compose config`, DB health, 데이터 보존·마이그레이션 영향 확인.
- 문서만 변경: 경로·링크·문서 간 상태·태스크 체크의 일관성을 확인한다. 코드 검사를 실행하지 않았다면 그렇게 기록한다.

M1 전에 Kakao SDK 이용 조건·등록 도메인·공개 JavaScript 키, 다산 지금지구의 검증된 중심 좌표·반경, mock 10곳의 **가상 데이터 표시**를 확인한다. DB가 필요한 작업 전에는 Compose 컨테이너의 health를 확인한다. 장소 수집과 AI 처리는 [데이터 정책](data-policy.md)의 권한 확인 전까지 시작하지 않는다.
